# Frontend deployment — dev / test / prod

The Teaching Tracker frontend is hosted on **Azure Static Web Apps**, one
resource per environment, each talking to its matching Function App
(`func-teaching-tracker`).

```
Frontend (Static Web App)              API (Function App, separate repo)
  swa-teachtracker-dev    ─── /api ──▶  func-teachtracker-dev-xxxx
  swa-teachtracker-test   ─── /api ──▶  func-teachtracker-test-xxxx
  swa-teachtracker-prod   ─── /api ──▶  func-teachtracker-prod-xxxx
```

## How an environment connects to its API

The only per-environment knob is **`VITE_API_BASE_URL`**, baked into the bundle
at build time. All API access goes through [`src/api/client.ts`](../src/api/client.ts);
components never reference a hostname.

- **Set** (e.g. `https://func-teachtracker-dev-xxxx.azurewebsites.net/api`) →
  the app calls that Function App.
- **Empty** (local dev, tests, CI unit tests) → the app runs on bundled seed
  data ([`src/data/students.ts`](../src/data/students.ts)), no backend needed.

Because the URL is compiled in, **each environment is built separately** with
its own value — the pipeline does not promote a single artifact across envs.

> Migration note: to move to a Static Web Apps **Standard** linked backend later
> (same-origin `/api/*` proxy, no CORS), set `VITE_API_BASE_URL=""` so requests
> become relative, link each SWA to its Function App, and drop the CORS config
> below. No component code changes.

## Environment mapping

| Environment | Static Web App        | Function App             | GitHub Environment |
| ----------- | --------------------- | ------------------------ | ------------------ |
| dev         | `swa-teachtracker-dev`  | `func-teachtracker-dev-*`  | `dev`            |
| test        | `swa-teachtracker-test` | `func-teachtracker-test-*` | `test`           |
| prod        | `swa-teachtracker-prod` | `func-teachtracker-prod-*` | `prod`           |

## Infrastructure

Terraform in [`infra/terraform`](../infra/terraform) creates one resource group +
one Free-tier Static Web App per environment.

```bash
cd infra/terraform
az login
terraform init
terraform apply           # creates dev, test, prod Static Web Apps

# Read the outputs you'll need for GitHub config:
terraform output static_web_app_urls          # -> Function App CORS origins
terraform output -raw static_web_app_api_tokens   # -> per-env deploy tokens (sensitive)
```

> Static Web Apps only exist in a few regions (`eastus2`, `westus2`,
> `centralus`, `westeurope`, `eastasia`) — **not** `eastus`. Default is `eastus2`.

## One-time GitHub configuration

Create three GitHub Environments (`dev`, `test`, `prod`) in this repo, and in
each set:

| Kind     | Name                              | Value                                                        |
| -------- | --------------------------------- | ------------------------------------------------------------ |
| Variable | `VITE_API_BASE_URL`               | The env's Function App hostname + `/api` (from the API repo's `function_app_hostnames` output) |
| Secret   | `AZURE_STATIC_WEB_APPS_API_TOKEN` | The env's SWA deploy token (`terraform output static_web_app_api_tokens`) |

On the **`prod`** environment, add a protection rule → **Required reviewers**,
so production waits for manual approval.

## CORS (in the API repo)

The browser calls the Function App cross-origin, so each Function App must allow
its paired SWA origin. In `func-teaching-tracker`'s Terraform, set per env:

```hcl
environments = {
  dev = {
    # ...
    cors_allowed_origins = ["https://swa-teachtracker-dev.azurestaticapps.net"]
  }
  # test, prod similarly
}
```

Use the exact URLs from this repo's `terraform output static_web_app_urls`.

## Deploy pipeline

[`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml) runs on push to
`main` (or manual dispatch) and promotes:

```
dev  (auto)  ──▶  test (auto, after dev)  ──▶  prod (after approval)
```

Each job (via the reusable [`deploy-env.yml`](../.github/workflows/deploy-env.yml))
checks out, `npm ci`, `npm run build` with that env's `VITE_API_BASE_URL`, then
deploys `dist/` to that env's Static Web App using its deploy token.

## Retiring the old single-env workflow

The original autogenerated workflow
`.github/workflows/azure-static-web-apps-black-bush-0b275e510.yml` deploys to a
single legacy Static Web App on every push to `main`. Once the dev/test/prod
setup above is live, **delete that file** (and optionally the legacy SWA
resource) so you don't double-deploy.
