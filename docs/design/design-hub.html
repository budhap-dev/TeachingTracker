Teaching Tracker — whole-system design

A tutoring tracker, drawn from the source up.

Technical & interface design across two repositories — a React SPA and an Azure Functions API with Terraform infrastructure. Reverse-engineered from code, so every claim is checkable.

SPA · React 18 + Redux-saga API · Azure Functions v4 · Node 24 Store · Azure Table Storage Auth · Entra ID + Key Vault v1.0.0

01 Overview

A private, single-teacher tool for students, classes, monthly payments, and per-student dated notes.

A browser SPA talks to a stateless HTTP API that persists to Azure Table Storage. Microsoft Entra ID provides sign-in; a teacher allow-list held in Key Vault authorises. Four design tenets shape everything:

Tenet 01

The API owns truth

Bills and payment status are derived server-side from classes actually held. The client never recomputes what is owed.

Tenet 02

Config over code

One API artifact; behaviour comes from app settings. The SPA is built once per environment because Vite inlines config.

Tenet 03

Keyless everywhere

CI deploys via GitHub OIDC; the API reaches storage and secrets through its managed identity and AAD RBAC.

Tenet 04

Graceful degradation

Auth is a flag — when not enforced the API logs "would refuse" and proceeds, so the app works before sign-in is switched on.

03 Frontend

React 18 + TypeScript + Vite, one Redux slice, all async through sagas, all HTTP through one wrapper.

State & the request lifecycle

A single RTK slice state.students holds the students, scheduledSessions and paymentsByMonth collections, three loading flags, three saving flags, a sticky error, and a transient notice toast. Every mutation follows one shape: request → saga → API → succeeded/failed. The *Succeeded reducer merges the server's returned record and raises a success toast; *Failed sets the error and an error toast.

Invariant
recalculateTotals recomputes only totalReceived = Σ amountPaid and totalOutstanding = max(due − received, 0). totalDue is summed from the API's per-record amountDue — never re-derived from fees on the client.

Routing & auth-less mode

Ten routes; eight teacher-gated by a RequireTeacher wrapper, two public (/offerings, /contact). Route wrappers filter archived students out of every active surface. The student page is one component with two deep-linkable tabs — /students/:id (Details) and /students/:id/diary (Diary). When the three VITE_ENTRA_* vars are unset the app runs auth-less: no MSAL provider, requests go tokenless — the mode tests and local dev use.

04 Backend

Thin Azure Functions handlers over services over a two-adapter DataStore.

Handlers validate and delegate; logic lives in studentService, sessionService, paymentService. Notable rules: a group class is N session rows sharing a groupId; archiving cancels (never deletes) future classes; and bills are derived, never stored — only a PaymentSettlement (amountPaid + notes) persists.

07 Security

Two walls: single-tenant Entra sign-in, then a Key-Vault email allow-list.

  • Sign-in — single-tenant (AzureADMyOrg) SPA + API app registrations; the API issues v2.0 tokens and exposes one scope, access_as_teacher.
  • Authorisation — JWT scope check and an email allow-list (teacher-emails in an RBAC Key Vault), fail-closed if the vault is unreachable.
  • Keyless CI — per-env GitHub OIDC, subject repo:owner/repo:environment:<env>; a dev job can't assume the prod identity. Each identity is Contributor on its app RG only.
  • Keyless data — the Function App's managed identity holds Table Data Contributor on the data account and Key Vault Secrets User on the vault. No account keys in code.
